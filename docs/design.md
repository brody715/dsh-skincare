# DSH Skin Care 设计文档（v1）

> 一句话：把 AAD 公众科普变成普通人**学得会、用得上、可溯源**的护肤决策系统——而不是又一个会顺着你说的护肤聊天机器人。

## 1. 问题定义

护肤是信息严重不对称的领域：功效宣称多、证据少、利润集中在「修复 / 淡印 / 抗老」这类模糊地带。普通人真实的痛点只有三个：

1. **不知道什么是有证据的基础**——被营销带着走，把钱花在叠加步骤上。
2. **分不清「自己能处理」和「必须看医生」**——要么过度医疗化，要么把病当皮肤问题养。
3. **没有可执行、可复盘的系统**——听过很多道理，routine 一周就崩。

已有的 AI 聊天能讲道理，但有三个结构性缺陷：来源不可查、容易顺着用户说、没有状态和进度。这个 Skill 就是来补这三点的。

## 2. 产品主张

**价值不在「回答护肤问题」，在于把有出处的皮肤健康知识，变成普通人能理解、能执行、能调整的东西。**

因此判断做得好不好的标准不是「答得像专家」，而是：

- 用户能不能**说出**自己为什么这么做（认知变了）；
- 用户的护肤步骤有没有**变少**（少买东西也是好结果）；
- 该看医生的人有没有**去看医生**（分诊正确）；
- 每一条结论能不能**点回 AAD 原文**（可溯源）。

## 3. 能力四层

| 层 | 名字 | 用户说什么 | 产出 |
| --- | --- | --- | --- |
| 查 | 有据可查 | 「A醇能不能和酸一起用」 | 结论 + 引用 + 可展开原文 |
| 学 | 系统学习 | 「我想系统学护肤」 | L0–L3 路径 + 每课自测 |
| 评 | 状态评估 | 「我该怎么弄」 | `profile.json`：认知阶段 / 护理复杂度 / 主诉分诊 |
| 跟 | 目标执行 | 「帮我定个目标」 | 可勾选行为清单 + 周复盘 |

四层共用一份**用户档案**（`~/.dsh/skin-care/profile.json`），插件阶段读同一份文件——这是 Skill 和插件能共用产品内容的接缝。

## 4. 硬性边界（不可协商）

1. **不诊断疾病**：可以说「这类表现常见于 X，需要医生确认」，不能说「你这是 X」。
2. **不开药、不给处方浓度**：涉及处方药（维A酸、抗生素、激素）只讲「医生可能会怎么考虑」。
3. **不做产品测评/带货**：不排品牌、不比价格、不推链接；可以讲「怎么读标签、怎么挑类别」。
4. **红旗必转诊**：见 `references/10-何时就医.md` 的红旗清单，命中即建议就医，不再给自我处理方案。
5. **不替代医生**：所有方案页脚注明这是科普整理，不是医疗建议。

## 5. 知识结构：为什么要拆「修复」

用户原始表述是「护肤 保湿 防晒 修复（消炎、淡化痘印）」。**「修复」是这套体系里最容易被商业化利用的词**，必须拆成三类，否则整个产品的可信度就没了：

| 口语说法 | 实际可能是什么 | 处理路径 |
| --- | --- | --- |
| 「屏障受损/敏感」 | 皮肤屏障功能受损、刺激性接触性皮炎 | 减法 + 保湿 + 停刺激物；持续则就医 |
| 「发炎/消炎」 | 痤疮炎性皮损、玫瑰痤疮、脂溢性皮炎 | **疾病范畴**，需医生确认，护肤只做辅助 |
| 「痘印」 | 红色痘印（PIE，血管性）/ 褐色痘印（PIH，色素性）/ 凹陷性瘢痕 | 三者机制不同、处理不同；瘢痕护肤无效 |

所以知识库按「**基础维持 → 问题处理 → 医疗边界**」三层组织，而不是按产品品类组织。

## 6. 目录结构

```
dsh-skincare/
├─ README.md                 项目说明（双交付物：Skill + 插件）
├─ ATTRIBUTION.md            AAD 内容版权与使用范围
├─ LICENSE                   代码 MIT；文字内容另有说明
├─ docs/
│  ├─ design.md              本文件
│  ├─ research/benchmark.md  开源 Skill / DSH 插件组织方式调研
│  └─ eval.md                评测方法与结果
├─ skill/                    ← 第一交付物：可独立安装的 Skill
│  ├─ SKILL.md               入口：触发条件、四种模式、读取顺序
│  ├─ references/            中文知识模块（按需读取，不塞进 SKILL.md）
│  ├─ agents/                专家角色提示词（评估师 / 导师 / 方案梳理 / 就医准备）
│  ├─ sources/               原始来源：索引 + 主题树 + AAD 原文副本
│  └─ scripts/               语料挖掘、检索、档案读写
├─ lib/skill.js              ← 主交付物：把 skill/ 注册成随包技能提供者
├─ lib/panel.js              ← 第二交付物：dsh-go 手机原生面板（可选，无 dshGo 的宿主不加载）
└─ eval/                     评测用例、跑分脚本、A/B 对照（ab.py / ab-v0.1.md）
```

**为什么 Skill 单独一层目录**：Skill 要能被单独安装（`cp -r skill ~/.dsh/skills/dsh-skincare`），插件目录不能污染 Skill 的加载面。同一个仓库两种交付物，各自可独立取用。

## 7. 引用机制（可溯源的关键）

知识模块里每个事实性结论后面挂标记：

```
洗面奶洗完不紧绷就够了，不需要「深层清洁」。[s:skin-care-basics/care/face-washing-101]
```

- `[s:<slug>]` → `sources/index.jsonl` 里查 `url` / `title` / 原文文件路径。
- 用户问「凭什么」→ 展开 `sources/core/<slug>.md` 原文（英文）。
- Agent 写答案前用 `scripts/lookup.py` 核一遍，**禁止凭记忆编引用**。
- 没有出处的结论必须显式标注「以下是我的推断，不是 AAD 原文」。

## 8. 学习路径 L0–L3

| 级别 | 目标 | 内容 | 判据 |
| --- | --- | --- | --- |
| L0 认知校准 | 知道护肤能做什么、不能做什么 | 三件套为什么是底座；营销话术识别；产品品类地图 | 能说出 3 个「不需要买」的东西 |
| L1 基础执行 | 把清洁/保湿/防晒做对 | 各自的标准、常见错误、自查清单 | 连续 7 天执行记录 |
| L2 问题处理 | 按主诉分流 | 痤疮 / 痘印 / 敏感屏障 / 色沉 / 干燥 | 能判断自己属于「自我处理」还是「就医」 |
| L3 长期与边界 | 不被长期收割 | 抗老证据、医美边界、标签阅读、补剂真相 | 能读懂一个防晒标签的 SPF/PA/广谱 |

每课 3–5 分钟阅读 + 2–3 道自测题；不追求覆盖，追求「学完能改变一个行为」。

## 9. 状态文件

`~/.dsh/skin-care/profile.json`（Skill 与插件共用）：

```json
{
  "version": 1,
  "updated_at": "2026-11-22T00:00:00Z",
  "stage": { "knowledge": "L1", "care_complexity": "clean", "triage": "self-care" },
  "concerns": ["acne-marks", "dryness"],
  "routine": [ { "step": "cleanse", "product_type": "氨基酸洁面", "freq": "2/day" } ],
  "goals": [ { "id": "g1", "text": "连续 4 周保持 3 步", "since": "2026-11-22", "status": "active" } ],
  "log": [ { "date": "2026-11-22", "done": ["cleanse", "moisturize", "sunscreen"] } ],
  "learning": { "L0": "done", "L1": "in_progress", "L2": "todo", "L3": "todo" }
}
```

写入有两条等价路径，格式相同、都做原子写，不要手写 JSON：dsh-go 面板（`lib/panel.js`，`node:fs` 临时文件 + `rename`，不起子进程）负责打卡与学习进度；`scripts/profile.py` 负责面板没做的 `set-stage` / `set-concerns` / `add-goal` / `add-routine`。档案是**用户数据**，不入库。

## 10. 交付与开放边界

- **阶段 1（已完成）**：Skill 可用 + 自己真实用一周 + 评测；私有仓库。
- **阶段 2（已完成，2026-11-22）**：dsh-go 原生面板（0.2.0 起并入主包，`dshGo` 清单在根 `package.json`，代码在 `lib/panel.js`）。面板 `skin-care-panel`（`session.tab` + `features`，图标 `heart`），加一个输入框胶囊「今天怎么护肤」（只填进输入框、不自动发送）。面板只读档案，展示阶段 / 复杂度 / 分诊 / 主诉 / 今日流程 / 近 7 天打卡 / 目标 / L0–L3 学习进度；两个写回入口（今日打卡、标记一课完成）由插件自己用 `node:fs` 原子写档案（同目录临时文件 + `rename`），**不起子进程、不拼 shell、不依赖 Python**——插件的运行时依赖只有 Node 内置模块。写不进去（权限、目录不可写、档案超限）时只弹一句提示，不改文件、不往输入框塞命令。`$DSH_HOME/skills/dsh-go-plugin/kit/bin/check.mjs . --load` 通过（胶囊 1 · 面板 1，中英 × 两种投放位置均可渲染）。安装随主包一起走 `plugin_manager` 的 `install_bundle`。
- **命名**：0.2.0 起包名为 `@brody715/dsh-skincare`（原 `local-skin-care`），`package.json` 的 `name` 与 `cordis.patch.yml` 的 `name` 两处保持一致；插件 id（Cordis 内部名）为 `dsh-skincare`。
- **开源边界**：代码 MIT；`references/` 的中文知识模块与 Skill 结构可开源（CC BY-SA 4.0）。AAD 原文（`sources/core/`）与其中文机翻（`corpus/`）都**不随包发布**，也不进公开仓库：`skill/sources/index.jsonl` 只留元数据（slug / URL / 标题 / 主题），写作用时按 URL 读原文（英文即可）或由使用者自己拉取。因此 `references/` 要写到自己能讲清楚机制与数字，不依赖随包语料。

## 11. v1 明确不做

- 拍照识皮损 / 皮肤打分（准确率与责任都不成立）
- 成分打分、成分冲突库（伪精确，AAD 没有这种口径）
- 产品推荐与比价
- 医美项目决策建议（只讲边界，不给方案）
